# Review 方法

> 目标不是"这次找出几个 bug"，而是**让隐患暴露过程可重复、覆盖可数、结论可核**。
> 依据：用户指令「应该怎么样review。让你review你就头疼医头，没有体系化/全面化的发现隐患」。

## 一、上一轮为什么是"头疼医头"

上一轮的两条取样路径都有偏：

1. 审了**改动过的文件**——样本 = 我最近碰过的代码。
2. 写了围绕**已出过事的错误类型**的规则——样本 = 已经疼过的地方。

两者都是"嫌疑人筛选"，不是"全场遍历"。结果是：已知类缺陷被锁住，未知类缺陷一个没碰。

## 二、三步法

### 第 1 步：枚举全集，不猜

先把被审对象**数出来**，每一个都是一个必须交代的单元：

| 单元类 | 当前数量 | 怎么数 |
|---|---|---|
| ArkTS 文件 | 45（8722 行） | `find ... -name '*.ets'` |
| C++ 文件 | 7（2411 行） | `find ... -name '*.cc'` |
| N-API 导出 | 28 | 注册表 `{"name", nullptr, ...}` |
| 异步边界 | 266 个 `await/.then`；3 个 `@Concurrent` | grep |
| 定时器 | 1 个 interval，1 个 timeout | grep |
| TSFN | 4 条通道 | `native_to_arkts.cc` |
| 持久键 | 45 | `PrefKeys` |
| 生命周期单元 | 11 个 `aboutToAppear` | grep |

全集一旦列出来，"审完了没有"就变成**数行数**，而不是感觉。

### 第 2 步：用不变量遍历，不用可疑度遍历

对每个单元，问同样 7 个问题。可疑度靠人猜会漏，不变量不会。

| # | 不变量 | 违反后果 | 判定方式 |
|---|---|---|---|
| **I1** | 每个 acquire 在**所有退出路径**上都有 release | 泄漏 / 幽灵回调 / 进程冻结 | 可机检 + 人工看提前 return 与异常 |
| **I2** | 每个可变共享状态**恰有一个归属线程** | 数据竞争、偶发崩溃 | 人工建字段→线程表 |
| **I3** | 跨边界的值在**接收侧**校验 | 静默默认值 / UB | 可机检 + 逐导出建表 |
| **I4** | 每个错误要么带因传出，要么带注释刻意吞掉 | 现场销毁 | 可机检 |
| **I5** | 每个异步操作被属主的 teardown 取消/取代 | 关闭后写入、幽灵 setState | 人工逐页扫 |
| **I6** | 每个持久键有默认值 + 类型 + 迁移 | 升级后崩 / 错值 | 人工建表 |
| **I7** | 生命周期回调与资源获取成对 | 监听器/定时器泄漏 | 可机检 |

每个单元都要对 7 条给出 **CLEAN / N findings**，不许留空。

### 第 3 步：每条结论标证据等级

| 等级 | 含义 | 允许的措辞 |
|---|---|---|
| **E1** | 从代码可证明 | "这会导致……" |
| **E0** | 推断 / 未观测 | "推断存在……风险" |
| **E3** | 真机实测 | "已验证……" |

上一轮的教训：「`stateStyles` 挂在子 `Text` 上不触发」先被当成 E1 说，实际是 E0，真机上才坐实。**E0 不许写成 E1。**

## 三、失败模式清单（每个单元都过一遍）

null / undefined · 空集合 · 边界值（0、-1、最大值）· 并发 · 部分失败 ·
超时 · 重试 · 时钟与负数 · 整数溢出 · 超长与 unicode · 权限拒绝 ·
磁盘满 / 只读 · 进程中途被杀 · 旧版本升级

## 四、机制化 vs 人工

**能判定的必须进脚本**，否则下次改动就会悄悄退化。当前 `scripts/audit.mjs`：

| 检查 | 对应 | 类型 |
|---|---|---|
| `args-uninit` | I3 C++ 参数表 | 阻塞（已负向测试） |
| `resource-pairing` | I1/I7 | 阻塞（已负向测试） |
| `error-masking` | I4 | 阻塞 |
| `napi-drift` | I3 三方对齐 | 阻塞 |
| `rstring` | I6 文案 | 阻塞 |
| `build-config` | 构建不变量 | 阻塞 |
| `hardcoded-text` | I6 i18n | 阻塞 |
| `state-styles` | I7 UI 手势 | 阻塞 |
| `napi-status` | I3 | 建议 |

**判不了的**（线程归属、语义正确性、跨文件时序）走人工深读，但必须按单元记账。

## 五、覆盖账

见 `ledger.md`。一单元一行，7 条不变量各一列。空着 = 没审。

## 六、防退化

1. 现场发现的每个缺陷，先问「能不能反推成一条机检规则」；能就进 `audit.mjs`，并**负向测试**证明它会响。
2. 不能机检的，写进 `CLAUDE.md` 的 Verification Discipline，而不是只写进一次性报告。
3. 规则本身也要防退化：任何新检查必须有一次"故意写错 → 它必须报"的验证记录。
